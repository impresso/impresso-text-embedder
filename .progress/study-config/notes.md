# study-config — design notes

Step 5 of `research/chunking-eval`: refactor the four research CLIs
(`corpus_select`, `corpus_fetch`, `embed_sweep`, `query_generate`) so
all hyperparameters live in a YAML config file per *study*, instead
of being spread across per-module `DEFAULT_*` constants, Make
variables, and CLI flags. This is the scaffolding step 6 (TBD —
split the chunking-eval into two studies, one for docs that fit in
context and one for docs that exceed it) needs to be auditable.

## Why this step exists

The previous turn surfaced a real cross-step inconsistency: the
corpus-selection threshold (`min_tokens=4000`) and the embedding-sweep
chunk grid (`{512..8190}`) were chosen independently, and the result
was that scenarios `S5/S10/S15` (chunk_tokens=8190) collapsed to
"no chunking" for ≥90% of the corpus — wasting three rows of the
experimental matrix because at chunk_tokens=8190 docs ≤ 8192 tokens
go through the one-shot path, identical to the truncate baseline.

The bug was not in any single module. Each `DEFAULT_*` constant was
sensible in isolation. The failure was at the seams, and that's
exactly what a single-source-of-truth config prevents. After this
step, every parameter that defines a study (corpus filter, chunk
grid, query budget, model pin, S3 paths) lives in one YAML file that
can be reviewed top-to-bottom in five minutes.

## Scope (locked with the user)

- **One YAML per study with `extends:` for shared defaults**, not a
  multi-study YAML. Studies are independent experiments — give them
  independent files so git history is per-study and a typo in one
  cannot rewrite another.
- **Single-level `extends:` only** — no chains. Reasoning stays
  local: a study YAML and its base are the entire surface area.
- **Pydantic for validation** — already a transitive dep via
  `langchain-openai`, gives helpful errors on bad YAML, supports
  cross-field invariants natively. Plain `dataclass` would
  re-implement validation by hand.
- **PyYAML for parsing** — small, de facto standard, easy to mock in
  tests. Ruamel.yaml only justified if we needed round-trip comment
  preservation, which we do not.
- **Per-study scenario IDs reset to `S0..SN`** — auto-generated by
  `build_scenarios(cfg.scenarios)`, uniqueness is `(study_name,
  scenario_id)`. Globally namespaced ids (`A-S0..B-S15`) were
  considered but require renaming the runai job-naming convention
  for no clear payoff.
- **CLI flags survive as override knobs** — `--config <path>` is the
  primary entry, but `--limit`, `--n-per-lg`, etc. remain for one-off
  smoke tests. They override config values when present.
- **Path templating: every entry in `paths:` must contain `{study}`** —
  validated at config-load time. Two studies cannot accidentally share
  an S3 key or local path.
- **Output records gain `study_name` + `study_config_sha` fields** so
  artefacts in a unified data lake can be told apart even when the
  same study is re-run with edited YAML. SHA is the SHA256-12 prefix
  of the sorted-keys JSON dump of the merged config — order-independent,
  deterministic.
- **Operational knobs stay on the CLI, not in YAML** — `--limit`,
  `--no-upload`, `--local-corpus`, `--max-workers`, `--log-dir`,
  `--batch-size`. The YAML is for *research parameters* (what the
  experiment IS); CLI flags are for *how to run it this time*.

## Layout

```
configs/research/
  base.yaml              # cross-study invariants
  study-v1.yaml          # frozen snapshot of pre-refactor defaults
  study-A-fit.yaml       # extends base, docs <= 8192 tokens
  study-B-overflow.yaml  # extends base, docs > 16384 tokens
```

`base.yaml` is intentionally a partial — it omits the per-study
required fields (`study.name`, `corpus.min_tokens`,
`scenarios.chunk_sizes`) so loading it standalone errors at validation
time. That is the signal it's a mixin, not a runnable study.

`study-v1.yaml` reproduces the pre-refactor defaults exactly so we
can verify the refactor is mechanical: running the new pipeline
against `study-v1.yaml` must produce a manifest with the same 400
ci_ids in the same order as the existing `corpus-v1.jsonl.bz2`. Once
green, `study-v1.yaml` survives one cycle as a regression check, then
can be deleted.

## Schema (top-level)

| Block | Purpose |
|---|---|
| `study` | study name (slug) — substitutes into `{study}` in paths |
| `s3` | sandbox bucket + rebuilt-text bucket (defaults from production) |
| `paths` | local + S3 path templates; every value must contain `{study}` |
| `corpus` | langident input, languages, providers, OCR, year window, length window, sample size, seed |
| `embed` | model name + revision pin, precision, attention, unpad |
| `scenarios` | truncate baseline yes/no, chunker family list, chunk-size grid, aggregator |
| `query_generation` | endpoint, model, parallelism, temperature, output cap, retries, position buckets, query types |

`StudyConfig.resolve_path("corpus_s3_key")` substitutes
`study.name` and returns the final string. `StudyConfig.config_sha`
is the stable 12-char fingerprint for provenance.

## Mechanism

1. **`research/study_config.py`** (this turn) — Pydantic models +
   `load_study_config(path)`. Lazy-imports `yaml` so test code that
   builds configs via `StudyConfig.model_validate(...)` doesn't pay
   for the YAML parser. `extra="forbid"` on every model catches
   typos in YAML keys (e.g. `langauges:`) at load time.
2. **`research/scenario_builder.py`** (next turn — refactor of
   `scenarios.py`) — `build_scenarios(cfg.scenarios) -> list[Scenario]`.
   The hardcoded 16-row `_SCENARIOS` tuple is deleted; ids are
   auto-numbered `S0..SN` from `(truncate_baseline, chunkers,
   chunk_sizes)`.
3. **CLI refactor** (next turn) — each of the four CLIs gains
   `--config <path>`, plumbs the relevant section through to its
   existing dataclass (`SelectionConfig`, `GenerationConfig`,
   `EncoderConfig`, …). Existing per-flag overrides remain.
4. **Output schema** — `embed_sweep` adds `study_name` and
   `study_config_sha` alongside the existing `scenario_id` /
   `chunker` / `chunk_tokens` fields. `query_generate` adds the same
   to its query records.
5. **Makefile** — `STUDY ?= study-v1` becomes the primary variable;
   every target forwards `--config configs/research/$(STUDY).yaml`.
   The scenario list is derived from the loaded config:
   ```make
   SCENARIOS := $(shell uv run --quiet python -m \
     impresso_text_embedder.research.scenario_builder \
     --config configs/research/$(STUDY).yaml --list-ids)
   ```

## Acceptance bar

Step 5 is **done** when:

1. `study_config.py` schema + loader land with peer test file
   covering: load valid YAML, reject missing required fields, reject
   path template without `{study}`, reject `extends` chain, reject
   self-extends, reject unknown top-level key, deep-merge correctness
   across nested dicts, `resolve_path` substitution, `config_sha`
   stability under field reorder.
2. The four CLIs accept `--config` and reproduce existing
   defaults when run against `study-v1.yaml` — verified by a manifest
   diff against the existing `corpus-v1.jsonl.bz2`.
3. The Makefile is config-driven; the `SCENARIOS` shell-out reads
   from the loaded config.
4. CLAUDE.md decisions list gains a "Study-config YAML — single
   source of truth for research parameters" entry.

## What this step does NOT do

- It does **not** rerun the experiments. That is step 6
  (`study-A-fit.yaml` + `study-B-overflow.yaml` against the
  refactored pipeline).
- It does **not** touch the production CLI (`impresso-embed-create`,
  `impresso-embed-validate`). The production flow has its own config
  story (`EncoderConfig` + flags) and entangling them is out of branch
  scope per `CLAUDE.md → "Out of scope on this branch"`.
- It does **not** delete the existing `corpus-v1.jsonl.bz2` artefact
  in S3. We re-derive it from `study-v1.yaml` once the refactor is
  green; until then it stays as a regression reference.

## Rejected alternatives

- **Single multi-study YAML keyed by name** (e.g. `studies: {v1:
  ..., A-fit: ..., B-overflow: ...}`). Looks DRY at first; rejected
  because one study's typo can break loading for all studies, git
  diffs are per-block-not-per-file, and "what is this study's OCR
  cutoff?" stops being a one-file grep. The `extends:` pattern keeps
  the DRY win (cross-study invariants in one file) without the
  coupling.

- **TOML instead of YAML.** TOML is already in `pyproject.toml`, so
  the parser is in the stdlib (`tomllib`) for free. Rejected because
  TOML's nested-table syntax is awkward for the structures we have
  (lists of dicts, dicts of lists), and YAML's comment-rich syntax
  fits better with config files a human edits before each run.

- **Hydra (Facebook's config system).** Solves exactly this problem
  with composition, defaults override, command-line overrides, sweep
  generation. Rejected because Hydra owns the entry point (it wraps
  `main()` with `@hydra.main`), pulls a non-trivial dep tree
  (`omegaconf`, `antlr4`), and is opinionated about how runs are
  organized. For four CLIs and ≤4 studies, the ~200-line custom
  loader here is simpler and obvious.

- **Pydantic-Settings with env-var override.** Considered for `s3.*`
  and `query_generation.endpoint`. Rejected — env vars stay in `.env`
  for secrets only (`SE_*`, `RCP_API_KEY`). Mixing
  research-parameter env vars in would create a third source of
  truth alongside YAML and CLI flags.

- **Chained `extends:`.** A study could in principle extend
  `study-A-fit.yaml` to make a variant. Rejected because chains make
  reasoning non-local: to know what value a field actually has, you
  walk the chain. Single-level keeps it: study YAML + base YAML, end
  of story. If we ever need a third dimension (e.g. "study A with
  Italian instead of fr/de"), it's one new YAML, no chain needed.

- **Globally unique scenario ids `A-S0..B-S15`.** More grep-friendly,
  but requires renaming the runai job-naming convention
  (`embed-sweep-s3` → `embed-sweep-a-s3`) and `Sx` is already wired
  into the existing notes. Per-study reset with `(study, sx)` as the
  unique key is enough.

- **Auto-derive `chunkers` from the chunking registry**, so adding a
  new chunker module automatically appears in every study's grid.
  Rejected: research questions have specific design choices about
  which chunkers to compare; auto-pickup would silently add a
  chunker to study A when someone landed it for study B's sake.

- **Ship YAML configs for studies A and B in this step.** Rejected:
  this is the refactor step. Mixing in the new-experiments setup
  conflates two reviews — "is the config schema right?" and "are
  A/B the right experimental designs?". Step 6 lands the new YAMLs.

- **Pin chunker / aggregator names to a `Literal`** in the Pydantic
  schema. Rejected because that ties the schema module's import
  surface to the chunking + aggregation registries, and the schema
  module is meant to be import-light. Validation against the
  registry happens in `scenario_builder.build_scenarios` instead.

## Open items

- **`yaml` dep bump in `pyproject.toml`** — `pyyaml>=6.0` lands with
  this step.
- **Test coverage for `_deep_merge`** — peer test file
  (`test_study_config.py`) covers the cases listed in the acceptance
  bar above.
- **Migration of `.env.example` and `.env.docker.example`** — neither
  carries research-parameter env vars today, so no change needed; the
  config split (research params in YAML, secrets in `.env`) is
  already what they reflect.
- **Step 6 scoping** — once step 5 is green, step 6 lands
  `study-A-fit.yaml` (`min_tokens=4096, max_tokens=8192,
  chunk_sizes=[512..4096]`) and `study-B-overflow.yaml`
  (`min_tokens=16384, chunk_sizes=[512..8190]`), reruns the four
  pipeline steps against each, and emits a single comparative report.
  Eligibility-pool scan at `{8192, 12288, 16384, 20000}` is gated on
  step 5 completing — that scan needs the refactored corpus-select
  to be config-driven so we can run it under a `--limit`-style
  ablation cheaply.
